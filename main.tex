\section{Why GPU-native modeling, only for NLPs?}
% =============================================================
\begin{frame}{Why a GPU-compatible modeling language?}{LP / QP / DCP --- not strictly needed}
  \begin{columns}[T]
    \begin{column}{.58\textwidth}
      \begin{itemize}
      \item Canonical forms ($A, b, c$, ...) $\Rightarrow$ \alert{one-shot CPU$\to$GPU copy} of problem data
      \item Solver \alert{can iterate entirely on the device}
      \item Solution copied \alert{once back} to CPU
      \item Transfers can be an overhead, but the cost is \alert{amortized} over many solver iterations
      \item \alert{Existing GPU-native solvers} in this class already work this way: \texttt{CuClarabel}, \texttt{cuPDLP+}~\citep{luCuPDLPFurtherEnhanced2025}
      \item<2-> $\Rightarrow$ For LP / QP / DCP, a \alert{GPU-native modeling language may not add much value}
      \end{itemize}
    \end{column}

\begin{frame}{Why a GPU-compatible modeling language?}{NLP --- the picture is different}
  \begin{columns}[T]
    \begin{column}{.58\textwidth}
      \begin{itemize}\itemsep2pt
      \item Solver \alert{queries the modeling layer at every iteration} for
        $f(x),\; g(x),\; \nabla f(x),\; \nabla g(x),\; \nabla^2_{xx} L(x,\lambda)$
      \item Each query depends on the current iterate---\alert{no one-shot transfer}
      \item Without GPU-native callbacks, every iteration pays a CPU$\leftrightarrow$GPU round-trip: \alert{significant per-iteration overhead, no amortization}
      \item<2-> JuMP today does \alert{not} emit GPU-native callbacks. Fine: modeling infrastructure stays on CPU, \alert{as long as the callbacks themselves run on the device}
      \end{itemize}
    \end{column}
    \begin{column}{.40\textwidth}

\begin{lstlisting}
using GenOpt, JuMP, CUDA, MadNLP

@constraint(model, [i in 1:n], x[1,i] == x0[i],
    container = ParametrizedArray)                            # grouped constraint

@objective(model, Min,
    lazy_sum(0.5 * R[j] * u[i,j]^2 for i in 1:N, j in 1:p))   # grouped sum

set_optimizer(model, () -> GenOpt.ExaOptimizer(madnlp, CUDABackend()))
optimize!(model)
\end{lstlisting}
  \begin{itemize}
  \item Intercept JuMP's expression at construction time and route it to the ExaModels backend --- patterns survive intact, no scalar enumeration in the bridge.
  \item<2-> Minimal model rewrite: \texttt{container = ParametrizedArray} on \texttt{@constraint}, \texttt{lazy\_sum} on \texttt{@objective}
  \item<3-> A really cool proof-of-concept route --- I'm thinking about something else next.
  \end{itemize}

\section{Benefits of encoding the algebraic structure in the type}
% =============================================================
\begin{frame}{Benefits of encoding the algebraic structure in the type}
  \begin{itemize}\itemsep5pt
  \item \alert{\bfseries Portability}: same model code on \texttt{CPU()}, \texttt{CUDABackend()}, \texttt{ROCBackend()}, \texttt{OneAPIBackend()}, \texttt{MetalBackend()}, \texttt{OpenCLBackend()} --- one backend keyword switches hardware.
  \item<2-> \alert{\bfseries Performance}: type-stable end-to-end $\Rightarrow$ Julia compiler inlines AD code per pattern.
  \item<3-> \alert{\bfseries AOT compatibility}: works under \texttt{juliac --trim=safe} for standalone binaries (no runtime codegen in the hot path).
  \item<4-> \alert{\bfseries Two-stage + batch}: \texttt{TwoStageExaCore} for first-stage / recourse-stage structure; \texttt{BatchExaCore} for many independent NLP instances sharing a structure.
  \end{itemize}
\end{frame}

\section{Alternative: ExaModels as a JuMP backend for GPU}
% =============================================================
\begin{frame}{Alternative: ExaModels as a JuMP backend for GPU acceleration}{Path: more type stability in JuMP expressions}
  \begin{itemize}\itemsep4pt
  \item Use ExaModels as a JuMP \alert{backend specifically for GPU acceleration} --- JuMP stays the user-facing layer; ExaModels generates the GPU-native callbacks under the hood.
  \item<2-> Key enabler: \alert{more type structure} in JuMP's expression tree, so the JuMP $\to$ ExaModels conversion dispatches statically instead of paying per-element type inference.
  \item<3-> \alert{Not full type stability} --- the compile-per-pattern cost (previous slide) doesn't fit JuMP's broader audience.
  \item<4-> \alert{Just enough}: encode the algebraic operator and arity in the expression-tree type. Operand values remain runtime-flexible.
  \end{itemize}
\end{frame}
